# Local library storage

## Scope

Phase 2 stores the library entirely in the browser. The React application does not call Spring Boot while it boots, imports, lists, edits, opens a stored binary, or deletes a local book. Installable application-shell caching arrives in Phase 3 and reading engines arrive in Phase 4; this document covers the durable library foundation now implemented.

```text
React UI
  -> LocalLibraryService
      -> IndexedDB repositories (structured records)
      -> BookMetadataService (bounded PDF/EPUB inspection)
      -> OpfsBookBinaryStorage (copied binaries)
```

React components do not open IndexedDB or OPFS handles. The application service receives repository/storage contracts, which keeps a future Capacitor Filesystem implementation out of domain and UI code.

## IndexedDB schema

The database is named `reader-local-library` and is currently at schema version 2.

| Store | Key | Phase 2 contents |
|---|---|---|
| `books` | `id` | Application-owned book records and opaque binary references |
| `progress` | `bookId` | Reading progress repository foundation; normalized locators arrive with reader phases |
| `settings` | `key` | Locally persisted application settings |
| `binary-cleanup` | `reference` | Retryable OPFS deletion intent after cross-store partial failure |

Version 1 created `books`, `progress`, and `settings`. Version 2 adds book indexes, the cleanup store, and defaults for older book records. Upgrades run inside the IndexedDB version-change transaction; if the migration fails, the browser does not commit a partially advanced schema. Fresh and version-1 upgrade paths are automated tests.

Book records use UUIDs generated by `crypto.randomUUID()`. They expose references such as `opfs:v1:<opaque-id>`, never a path or browser file handle. The record supports title, author, description, publisher, language, identifier, format, cover/binary references, original filename, size, timestamps, status, favorite, page count, table of contents, and metadata provenance. User edits are recorded separately from extracted fields.

## OPFS binary storage

`OpfsBookBinaryStorage` gets the origin-private root through [`navigator.storage.getDirectory()`](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/getDirectory), creates an application-managed directory, and copies each selected file to an internal opaque name. OPFS contents are private to the origin and are not ordinary user-visible filesystem paths; clearing site data deletes them. See the [MDN OPFS overview](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system).

The adapter provides:

- `write(Blob)` returning an opaque reference;
- `open(reference)` returning a local `File`;
- idempotent `delete(reference)`;
- `exists(reference)`;
- quota/durability inspection and a persistence request.

It reports stable typed errors for unsupported storage, permission denial, quota exhaustion, a missing binary, an empty/corrupt binary, and unexpected I/O. A temporary object URL is never used as permanent storage. Phase 2 intentionally has no IndexedDB-blob fallback: if OPFS is absent, import fails clearly. A fallback may be added only behind the same contract with durability and migration tests.

## Durability and quota

The storage card displays the result of [`navigator.storage.estimate()`](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/estimate) where the browser supplies it and uses [`navigator.storage.persist()`](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist) when the user asks to protect local books. Persistence is a browser decision, not a guarantee the app can make. If it is denied or unavailable, the library can still work, but storage may be evicted according to browser policy.

Before a write, the adapter compares the estimate with the file size plus a small reserve. The actual OPFS write remains authoritative because estimates can change. Both a preflight shortage and a browser `QuotaExceededError` produce the same actionable quota error, and partial output is removed best-effort.

Users must retain their original files or separate backups. Phase 2 has no cloud backup, device-to-device transfer, full library export, or restore flow. Browser profile deletion, site-data clearing, origin changes, private-browsing cleanup, and device loss can remove the local library.

## Import validation and metadata

Imports are bounded to 512 MB. The importer checks file bytes rather than trusting the filename extension:

- PDF requires a `%PDF-` signature in its initial bytes. PDF.js reads the document locally for embedded metadata and page count with dynamic code evaluation disabled.
- EPUB requires a ZIP signature, the exact EPUB mimetype value, `META-INF/container.xml`, a safe package path, and a readable package document. Selected XML/HTML and cover entries have extraction bounds, archive paths are validated, and navigation markup is parsed inertly with `DOMParser`. Publication scripts are not executed.

The EPUB validation follows the required container shape in the [W3C EPUB Open Container Format](https://www.w3.org/publishing/epub32/epub-ocf.html). JSZip's path sanitization is treated as defense in depth; the importer also rejects entries for which JSZip reports an unsafe original path. Metadata extraction includes useful publication fields, cover data, and EPUB 3 navigation or EPUB 2 NCX entries when available. Missing optional metadata falls back to a title derived from the sanitized leaf filename.

The current metadata extraction reads the selected compressed file into memory. The 512 MB cap bounds the operation but does not make the upper limit appropriate for every mobile device; worker/streaming performance work is explicitly deferred to the Phase 4 reader and Phase 10 audit.

## Import and deletion consistency

Import uses this recoverable sequence:

1. validate signature, size, container paths, and required publication structure;
2. extract bounded metadata locally;
3. copy the book and optional cover into OPFS;
4. create a UUID-owned book record and commit it to IndexedDB;
5. if the structured commit fails, delete copied binaries; if immediate deletion also fails, queue cleanup intent.

The UI only reports success after the IndexedDB book record commits. Invalid, unsupported, oversized, or quota-exhausted imports therefore do not create phantom book records.

Deletion cannot atomically span IndexedDB and OPFS. The application first uses one IndexedDB transaction to delete the book and its progress while writing cleanup records for its book/cover references. It then deletes the OPFS files and clears each cleanup record. If that second step fails or the app closes, initialization retries pending cleanup; failed attempts remain recorded. The book is absent from the visible library as soon as the structured transaction commits.

Future annotation and collection stores must extend the same deletion policy in their owning schema migration. Phase 2 only has dependent progress data.

## Legacy server migration

The React primary flow no longer imports through `POST /api/books/upload`, and its old API client has been removed. The Spring endpoint remains temporarily for migration/backward compatibility and sends deprecation headers. It is a separate legacy server-side record; it does not populate the local library.

Phase 8 must deliberately remove it or replace it with authenticated, user-scoped, opt-in cloud backup semantics backed by object storage. It must not silently survive as a competing import authority.

## Manual validation checklist

Use a secure-context browser with OPFS support and keep Spring Boot and MongoDB stopped.

1. Start the Vite client and import one valid PDF and one valid EPUB.
2. Reload the page and confirm both records remain.
3. Edit a title/author, reload, and confirm the edit remains.
4. In browser developer tools, confirm `reader-local-library` records exist in IndexedDB and copied `.bin` objects exist under the origin-private filesystem.
5. Delete a book and confirm its record and managed binary are removed.
6. Try a renamed text file, malformed EPUB, and a file beyond available quota; confirm no phantom record appears.
7. Stop/restart the frontend at the same origin and confirm the library remains. Full offline application-shell reopening is Phase 3 work and is not claimed here.
